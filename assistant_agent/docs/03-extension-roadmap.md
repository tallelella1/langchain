# 扩展路线与取舍

本文件中的能力都是后续选项。P0 是首版课件闭环；P1 先改善可观察到的质量问题；P2 再扩展使用方式；P3 面向多人使用与长期运维。只有进入相应阶段时才创建目录、引入依赖。

## 1. 分阶段选择

| 阶段 | 能力 | 触发依据 | 价值 |
| --- | --- | --- | --- |
| P0 | 单 TXT、固定检索、无工具 Agent、来源展示 | 课件 2.5.3 | 建立可解释、可验证的 RAG 闭环 |
| P1 | 章节切分、相邻／父块补全 | 退款、计费规则的适用条件被切散 | 提高事实覆盖，减少断章取义 |
| P1 | 混合检索与重排 | 关键词明确的问题仍召回不准 | 改善术语、数字与语义检索的互补性 |
| P1 | 文档版本、更新与删除 | 需要更新 2026 Q1 素材或加入第二份文档 | 避免旧知识与新知识混用 |
| P1 | 固定评估集与参数实验 | 开始调整参数或模型 | 用同一基线判断改动是否有效 |
| P2 | 多格式导入 | 用户实际需要 PDF、Markdown、DOCX | 扩大知识来源并保留页码等证据 |
| P2 | 多轮对话与流式输出 | 出现“那专业版呢”等连续追问 | 改善交互与首字等待体验 |
| P2 | 检索工具型 Agent | 确实需要自主选择检索或多个只读工具 | 支持多次检索与步骤决策 |
| P2 | FastAPI 与页面 | 需要浏览器交互或外部调用 | 复用核心逻辑，提供独立服务入口 |
| P3 | 多知识库、权限、任务管理、观测 | 多人、多数据源、长期运行 | 保证隔离、可维护性与问题定位 |
| P3 | 知识图谱／GraphRAG | 存在跨文档实体关系与多跳问题 | 覆盖简单向量检索难以表达的关系 |

## 2. P1：先改善质量

### 2.1 章节切分与父块补全

**接入位置：** `rag/documents.py`、`rag/retrieval.py`。

1. 先保存 220/80 基线结果。
2. 识别一级章节、套餐名、规则小节，把标题写入片段元数据。
3. 避免只有分隔线或标题的片段成为独立有效知识；保持规则与适用范围关联。
4. 可采用“小块检索、大块提供上下文”：检索命中子块，再按 `parent_id` 取得完整规则段。
5. 保留子块到父块的引用映射，避免上下文补全后来源失配。

**验收：** 比较 Q03–Q06 的事实覆盖；上下文包含退款主规则、升级和发票条件；记录上下文长度变化，而不是单纯认为块越大越好。

### 2.2 混合检索与重排

**接入位置：** `rag/retrieval.py`，需要时再增加 `rag/reranking.py`。

流程候选：语义召回与 BM25 关键词召回分别取候选，按统一 ID 去重／融合，再用重排模型选出最终上下文。可以用 RRF 融合名次，避免直接相加不可比较的 BM25 与 COSINE 分数。

Milvus 服务端全文检索是否可用、如何建稀疏字段与分析器，应依据实际版本核验；不因为框架支持“混合检索”就假定当前集合已具备该能力。若使用内存 BM25，需定义中文分词与索引更新方式。

**验收：** 对“增值税专用发票”“API 超额”“刚好 50%”等题比较事实覆盖、最终排名、延迟与额外模型调用；只有改善被验证后才保留复杂度。

**阈值：** 用已标注的可回答与不可回答问题校准。重排分数和余弦分数分别处理，不直接沿用某个项目的 0.5 或 0.7。

参考：[Open WebUI 的 RAG 功能说明](https://github.com/open-webui/open-webui)、[RAGFlow 的切分与引用能力](https://github.com/infiniflow/ragflow)。这些是可借鉴能力，不代表其实现可以无修改移入本项目。

### 2.3 知识更新、版本与删除

**接入位置：** `ingest.py`、`rag/vector_store.py`；进入这一阶段再增加索引元数据文件或存储。

建议新增 `doc_id`、`content_hash`、`document_version`、`index_version`、`embedding_model` 与切分配置摘要。多文档使用稳定主键策略，不能继续让每份文件从 `id=0` 开始写入同一集合。

本项目优先采用“新版本集合构建完成后切换”的清晰路线：

1. 计算源文件与索引配置摘要，判断是否需要更新。
2. 在新集合完成解析、切分、向量化与写入。
3. 校验记录完整性并通过固定问题集。
4. 在受控维护中切换当前集合引用；如使用 Milvus alias，先核验所用版本接口和切换语义。
5. 新请求使用新版本，进行中的请求保持一致的集合目标。
6. 旧集合按明确保留策略回收，以便失败时回退。

这是未来替代首版“已有非空集合即停止”的维护方案。若修改主键类型或 schema，使用新集合迁移，不能原地假定兼容。

**删除语义：** 删除文档后，新检索不再召回它；历史答案如何保留引用另行定义。向量、原文及元数据删除应能核对，不能只在页面隐藏名称。

**验收：** 测试重复导入、文件变短、文档删除、Embedding 更换、构建中断和切换失败；旧片段不残留，新索引失败时旧版本仍可用。

### 2.4 固定评估集

**接入位置：** 后续增加 `evals/`，保存问题、期望事实、支持段落与结果。

- 用 `Recall@K` 或“所需事实被召回的比例”观察检索；多条件问题需要覆盖全部必要条件，单个相关片段不代表完整回答。
- 答案评价关注事实正确、证据支持、引用准确和拒答表现。
- 记录实际延迟、输入上下文长度、模型标识与可获取的用量数据。
- 对比实验一次只改变一个主要因素，保留数据版本；新增问题进入下一版评估集，避免只围绕已见题调参。

首版 12 道验收题可作为起点。LLM 裁判属于辅助评价，不替代关键事实与边界条件的人工核对。

## 3. P2：扩展数据与交互

### 3.1 多格式知识源

**接入位置：** `rag/documents.py` 扩展为 `rag/loaders/`；先按真实数据类型增加一个 Loader。

PDF 保留页码，Markdown 保留标题层级，DOCX 保留段落与标题。扫描 PDF 再单独评估 OCR；识别、表格重建与引用定位分别验收。`asset/load/` 中已有学习素材不自动视为正式客服知识。

**验收：** 页面展示的来源能定位到实际页／段；表格字段对应关系没有被扁平化破坏；解析失败会报告，不能作为空文本成功入库。

参考：[RAGFlow](https://github.com/infiniflow/ragflow) 的文档处理、[AnythingLLM](https://github.com/Mintplex-Labs/anything-llm) 的文档收集与问答分工。

### 3.2 多轮追问与流式输出

**接入位置：** `rag/answering.py`，需要时增加 `rag/conversation.py`。

对“基础版多少钱？”之后的“那专业版呢？”先结合历史明确本次检索问题，再检索知识库。保留原始当前问题用于最终回答；历史回答不能代替知识事实。会话 ID、最近轮次和当前消息是否进入请求应有明确约定。

流式输出先保证非流式返回结构稳定，再增加事件：开始、答案增量、来源、完成、错误。流中断不得发送正常完成标记；重连是否支持及是否重复计费由实际接口能力决定。

**验收：** 追问指代正确；更换话题不会误带旧条件；两个会话不串话；异常能与正常结束区分。

### 3.3 检索工具型 Agent

**接入位置：** 将既有 `retrieve` 包装为只读工具，修改 Agent 初始化。

只有需要自主选择检索、重写查询或综合多个只读工具时才采用。先比较与固定检索基线的正确率、调用次数及延迟。工具描述应明确输入、来源与无结果语义；调用预算依据产品需求设定，不任意添加次数限制或重试。

**验收：** 客服知识问题实际使用检索证据；不会虚构工具执行结果；工具失败明确反馈；在简单问题上仍达到基线质量。参考 [LangChain Retrieval](https://docs.langchain.com/oss/python/langchain/retrieval)。

### 3.4 API 与页面

**接入位置：** 新增 `api/`；核心 RAG 模块继续复用。

规划接口包括：单次问答、可选流式问答、知识入库任务创建、任务状态查询。健康检查区分进程存活与依赖就绪。上传和建索引属于管理操作，不能复用普通聊天权限。

最小页面先展示问题、回答、来源与错误；知识管理页再展示文件状态、索引版本和导入失败原因。长文档导入需要任务状态后，才引入后台任务与队列。

**验收：** API 与终端使用同一核心逻辑；前端引用与本次返回来源一致；导入任务失败不会显示“知识库已就绪”。

## 4. P3：多人使用与长期维护

| 能力 | 必要设计 | 验收重点 |
| --- | --- | --- |
| 多知识库与权限 | 用户／知识库关系、检索前鉴权、服务端过滤、缓存隔离 | 无权文档不能进入召回结果或 Prompt；不能只在页面隐藏 |
| 并发索引任务 | 同文档版本互斥、任务状态、幂等写入与恢复 | 两次导入不互相覆盖，失败任务不发布为可用版本 |
| 观测与反馈 | 请求 ID、索引版本、阶段耗时、召回 ID、用户反馈 | 可以定位慢在解析、检索还是模型；不记录密钥 |
| 缓存 | 以问题、知识版本、模型和权限范围组成缓存键 | 更新知识或权限后不会读到过期／越权答案 |
| 生产部署 | 明确版本、持久卷、备份恢复、资源配置与就绪检查 | 重启与恢复后数据完整；不靠容器启动成功证明服务可用 |
| 图检索 | 实体抽取、关系来源、图版本与向量检索的组合 | 多跳题有实际改善，关系可追溯，错误关系可修正 |

这些扩展不改变首版学习目标。只有实际进入多人服务时才设计完整租户隔离与运维方案。

## 5. 按需增加的文件树

下面是扩展位置示意，不与首版同时创建，也不承诺需要全部目录。

```text
assistant_agent/
├── rag/
│   ├── loaders/             P2：多格式导入
│   ├── reranking.py         P1：候选重排
│   ├── conversation.py      P2：多轮问题整理
│   └── tools.py             P2：只读检索工具
├── api/                     P2：Web 服务与接口数据结构
├── web/                     P2：需要独立页面时再建立
├── jobs/                    P3：有并发长任务需求后再建立
├── evals/                   P1：固定问题集、证据标注、对比结果
├── data/                    P1：版本清单／解析产物，单独定义忽略规则
└── deploy/                  P3：按实际服务版本编排部署
```

建议执行顺序：P0 闭环 → 固定评估集 → 切分与检索优化 → 索引版本 → 按真实使用需求选择多轮或 API。GraphRAG、多 Agent、可视化工作流不作为当前前置条件。
