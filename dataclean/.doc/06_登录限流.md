# 06 登录限流：分布式限制认证请求

> 状态：实施指南，尚未实现。可先于密码找回独立实施。

## 1. 当前实现与风险

当前 [api.py](../app/api.py) 的 `/api/auth/token` 会查询用户并验证 Argon2 密码，没有请求频率限制。多个 API 实例独立内存计数也无法形成统一限制。大量错误密码请求既可猜密码，也会消耗密码哈希计算资源。

目标是在昂贵的密码验证前做分布式限流，限制单来源、单账号及账号与来源组合的攻击；对不存在的账号执行相同策略，避免用限流响应推断用户是否存在。

## 2. 建议规则与产品表现

以下数值是低流量首版的起点，需要用实际共享出口、失败比例和压测调整。

| 维度 | 示例阈值 | 目的 |
| --- | --- | --- |
| 来源 IP 的全部登录尝试 | 60 秒 30 次 | 限制同来源轮换用户名 |
| 账号摘要 + 来源 IP | 60 秒 5 次 | 限制对单账号集中尝试 |
| 账号摘要的全部尝试 | 5 分钟 30 次 | 约束多来源对同账号的持续尝试 |
| 找回邮件，来源 IP | 10 分钟 20 次 | 限制批量发送 |
| 找回邮件，邮箱摘要 | 15 分钟 3 次 | 限制邮件轰炸 |
| 确认重置，来源 IP/令牌摘要 | 分别设置短窗口预算 | 限制重复提交与猜测 |

首版对**所有尝试**计数，而不是只统计失败，便于在执行密码哈希前拒绝。正确密码也不能绕过当前请求预算；登录成功不能把整个 IP 或账号尝试计数清零。

超过窗口返回 429，正文统一 `too_many_attempts`，包含不泄露账号存在性的提示，并设置 `Retry-After` 为该次触发限制的剩余秒数。前端在倒计时后允许再次提交，切勿永久锁定账号。

账号维度的短期限流也可能被攻击者用来暂时阻碍真实用户，因此采用有限冷却，监控误伤，必要时后续加入经过验证的额外认证通道。首版没有验证码时不能声称已彻底解决分布式撞库或拒绝服务。

## 3. Redis 原子实现

Redis 官方的 INCR 限流示例说明，分别执行计数与过期设置存在竞争，可用 Lua 合并，见参考 [1]。

建议新增 `app/rate_limit.py`，单个维度的设计 Lua 如下。这是实现骨架，需要在项目客户端封装与错误策略中集成：

```lua
local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
end
local ttl = redis.call('PTTL', KEYS[1])
return {count, ttl}
```

服务端验证窗口参数为正数且在配置允许范围内；计数大于阈值即拒绝，Retry-After 使用 TTL 向上取整。观察到无过期 TTL 的限流键属于状态异常，应报警并进入明确故障策略，不能无限封锁用户或静默放行。

键示例：

```text
dataclean:prod:rl:login:ip:<ip_digest>
dataclean:prod:rl:login:pair:<account_ip_digest>
dataclean:prod:rl:login:account:<account_digest>
```

摘要建议用服务端专用密钥的 HMAC，输入使用明确的规范化用户名/邮箱及可识别的 IP；避免在 Redis、日志中直接暴露邮箱和用户名。普通无盐 SHA-256 仍可能被字典反查。

每个请求执行相关维度计数，只要一个超限就拒绝；即使最终拒绝，本次尝试也保留计数，这是规则的一部分。可将独立单键脚本 pipeline，减少往返，但不要把客户端 pipeline 当作多键事务。

当前 Compose 使用独立 Redis 实例。未来切到 Redis Cluster 时，多维键可能不在同一 hash slot；保持单键 Lua，或重新设计槽位策略，不能直接把跨槽多键脚本搬过去。

## 4. 登录限流流程与执行顺序

1. 先限制登录请求体大小，防止解析超大表单。提取用户名后按与注册/登录相同的规则规范化。
2. 获取受信任的来源 IP，计算 HMAC 限流键，不在日志输出原密码。
3. 原子计数并检查全部规则。超限立即 429，不执行用户查询与密码哈希验证。
4. 未超限后执行现有认证；用户名不存在与密码错误仍返回相同 401 和提示。
5. 不存在的账号也使用固定的有效 dummy hash 做验证，降低明显的存在性时延差异；不要每次生成 dummy hash，避免额外计算消耗。
6. 成功后签发 JWT，记录低基数结果指标。若另外实现“失败连续次数”，成功仅清理该专门计数，不重置全部尝试预算。

当前 login 是同步 `def` 路由，可以保持同步 Redis 客户端并沿用 FastAPI 对同步路由的线程执行方式，依据见参考 [4]。将来改为异步路由时，应使用异步 Redis 客户端或明确安排线程执行；不要直接在事件循环里引入长时间同步网络等待。客户端连接/读超时应基于登录延迟目标设置并验证，不从无限等待开始。

## 5. 反向代理与真实 IP

阿里云常见链路为浏览器 → HTTPS 入口/负载均衡 → Nginx → Uvicorn。若始终拿到代理地址，会让所有用户共享限额；若无条件相信 X-Forwarded-For，攻击者可伪造 IP 绕过限制。

Uvicorn 提供 proxy headers 与受信任来源配置，见参考 [3]。实际实施应：

- API 端口仅允许受信任代理访问，保留当前默认 127.0.0.1 绑定或使用受控内网入口。
- 入口覆盖/整理来自公网的转发头；多层代理明确每一跳可信地址。
- `--forwarded-allow-ips` 只配置真实代理来源或受控网段，不随意设为 `*`。
- 应用从配置好的请求来源接口读取 IP，不自行取 X-Forwarded-For 第一个字符串。
- 覆盖 IPv4、IPv6、共享 NAT 和多代理部署场景，检查限流误伤与绕过。

若使用 WAF/网关限流，可以增加外层保护，但应用账号维度的校验仍有独立价值。

## 6. Redis 故障策略

建议首版采用明确的 fail-closed：限流服务无法确认预算时，登录、找回邮件、重置确认返回 503 和统一的暂时不可用提示；不在异常处理中直接继续认证。记录 `rate_limiter_unavailable` 指标并告警。

已有 JWT 的普通任务查询无需依赖登录限流 Redis；它们仍按数据库鉴权规则工作。该策略牺牲认证入口短期可用性，以换取故障时不开放无限猜测，需要在上线前接受并演练。

不要给每个 API 实例加一个未说明的内存兜底：扩容后预算会被倍增，重启后限制归零。若未来需要降级，单独设计、评审并验证受控的集中应急方案。

Celery broker 与限流初版可以共用一个 Redis 服务、分开命名空间；不同 DB 编号不等于内存、故障和权限完全隔离。流量增长后使用独立实例/账号与资源预算，避免队列积压影响登录。

## 8. 上线与回滚

先用观察模式记录“本会拒绝”的次数，在测试账号模拟共享出口与错误密码；再启用低风险 IP/pair 规则，最后启用全账号规则。观察阶段明确仍无阻断保护。

部署切换保持规则版本和键前缀一致。阈值降低立即生效可能影响窗口内用户，应在变更说明中明确。回滚规则可恢复旧阈值，但不能通过 flushall 清空整个 Redis，那会影响任务队列。

HMAC 密钥轮换会改变键，需有短暂双读/双计数策略或接受一次窗口重置，不能声称轮换对限流状态毫无影响。

## 9. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 两台 API 同时对同键发出阈值以上请求 | 总允许数不超过规则预算 |
| 第一次计数后进程被强杀 | Lua 已原子设置 TTL，没有永久键 |
| 不存在账号与真实账号被限流 | 相同状态、正文和计数规则 |
| 反复伪造 X-Forwarded-For | 非可信来源不能改变应用识别的客户端 IP |
| Redis 停止/超时 | 认证入口 503；不静默执行密码验证 |
| 窗口到期 | 允许重新尝试，不永久锁账号 |
| 一次成功登录 | 不能清掉整个共享来源的请求预算 |
| SMTP 重置接口反复调用 | 邮箱/IP 两维限制均有效，响应不暴露邮箱是否存在 |
| 多账号共享公司 NAT | 测量误伤，按流量证据调阈值 |
