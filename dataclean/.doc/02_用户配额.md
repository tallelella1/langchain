# 02 用户配额：限制空间与任务占用

> 状态：实施指南，尚未实现。依赖 [01 的文件登记](01_多机对象存储.md)；本地存储也可使用相同账务模型。

## 1. 当前缺口与目标

[upload_limit.py](../app/upload_limit.py) 和 [api.py](../app/api.py) 已限制单文件 10 MiB，并检查实际接收字节数。但用户可以反复上传不同文件，累计占满磁盘或 OSS，也可以提交大量排队任务。`User` 当前没有配额，[jobs.py](../app/jobs.py) 也没有输出资源预算。

目标是：不同用户拥有独立预算，多台 API/worker 同时处理时也不能超卖；失败、重复提交、进程中断和自动清理后仍能算清占用。Redis 可以缓存展示结果，但 PostgreSQL 是持久配额账本。

## 2. 先明确业务规则

建议演示环境从以下数值起步，均属于可调整策略，不是已测容量。

| 配额 | 示例值 | 计算口径 |
| --- | --- | --- |
| 单次上传 | 10 MiB | 实际输入字节，保留现有边界 |
| 用户总空间 | 1 GiB | 已确认存在的输入、产物、未发布残留 + 尚未消费的写入预留 |
| 同时活跃任务 | 3 个 | 上传占位、queued、running 共用槽位；同一任务自动重试不重复占槽 |
| 每日提交 | 100 次 | UTC 日内新任务和显式手动重试；幂等重放与自动重试不增加 |
| 单次结果总量 | 50 MiB | 四个产物实际总字节，处理前预留，不够则明确失败 |

建议总空间不足返回 409 和 `quota_exceeded`，任务槽位或每日提交不足返回 429；429 携带明确的限制类型和可计算时的 `Retry-After`。前端要区分“删除文件可释放空间”和“等到下一 UTC 日恢复提交额度”。

失败任务仍保存输入供重试，因此空间不会因为状态变成 failed 就自动释放。过期文件只是不可访问，实际删除确认后才能释放空间。未被清理的私有产物也占物理空间，必须计入预留或已用空间。

## 3. 建议模型与不变量

| 模型 | 建议字段 |
| --- | --- |
| `UserQuota` | user_id、limit_bytes、used_bytes、reserved_bytes、active_limit、active_slots、daily_limit、updated_at |
| `DailyUsage` | user_id、utc_date、used_submissions、reserved_submissions；唯一约束 `(user_id, utc_date)` |
| `QuotaReservation` | id、user_id、operation_id、kind、reserved_bytes_remaining、reserved_slot、daily_date、state、expires_at |
| `QuotaEvent` | id、user_id、event_key、bytes_delta、reserved_delta、slot_delta、daily_delta、created_at |

`QuotaEvent.event_key` 全局唯一，例如 `asset:<id>:stored`、`asset:<id>:deleted`、`job:<id>:slot:release:<generation>`。同一事件重复处理只返回已有结算结果，不能二次加减。

关键不变量：

```text
used_bytes >= 0
reserved_bytes >= 0
used_bytes + reserved_bytes <= limit_bytes
active_slots <= active_limit
used_submissions + reserved_submissions <= daily_limit
```

`used_bytes` 表示已确认写入且尚未确认删除的登记文件；`reserved_bytes` 表示操作尚可写入的额度。一个已上传的文件不能同时全额计入 used 和 reserved。每个文件成功写入后，在短事务中从该操作的 reserved 转到 used；余量在操作关闭后释放。

未知结果的外部写入暂时保留对应预留，直到 HEAD/对账确认大小或删除确认。孤儿残留不应成为账外空间。管理员调低配额时，若新值低于当前占用，拒绝该修改或设置“只阻止新增”的专门策略；不能直接破坏不变量。

## 4. 上传流程：预留、结算、释放

1. 鉴权与基础参数校验后，创建上传操作。事务锁定 `UserQuota` 和当日 `DailyUsage`，检查空间、槽位、每日提交，预留 10 MiB、一个槽位和一次提交。
2. 提交事务后才接收并写入专用临时文件，不在网络传输期间持有行锁。临时磁盘由节点级预算控制；用户空间预留不能替代节点容量管理。
3. 对真实字节数、SHA-256 和幂等键完成校验。若是已有任务重放或 409 冲突，不创建新任务，关闭本次操作并释放未使用预留与槽位。
4. 新文件写入长期存储后，按 `FileAsset` 的实际大小结算；剩余输入预算释放。创建 Job、转正每日计数和转移槽位归属在同一数据库事务完成。
5. 单个用户两个请求并发到来时，行锁或带余额条件的 UPDATE 只允许预算范围内的请求成功。不能用“先 SELECT 检查、稍后普通 UPDATE”的方式扣减。
6. 如果已写长期对象后才发现幂等竞争失败，保留该对象的已用占用，登记删除；删除确认后再减空间。每日次数和业务槽位可以立即归还，因为该任务没有被接受。
7. 请求断线时，在能确认对象未生成的情况下释放预留；外部写入结果未知时保留登记和预留，04 的清理器确认后结算。

保守预留意味着用户剩余空间小于 10 MiB 时，即使实际文件很小也可能被拒绝。首版应把这一规则写进页面；后续可用有上限的声明大小预留并严格检查实际字节。不要信任 `Content-Length` 来绕过实际大小检查。

幂等重放最终不能重复计费，但在当前“读完文件才能证明内容相同”的接口下，空间完全耗尽时，重放也可能在临时预留阶段被拒绝。用户可直接查询已有任务。若要在满额时也保证重放可用，应另行设计有预算的幂等查询协议，不能省略内容冲突校验。

## 5. worker 输出与重试

### 执行前

`claim_job()` 抢占后，在相同锁序下为该 `run_token` 预留 50 MiB 输出额度。无输出额度时，将任务明确置为 failed 并给出“清理空间后可重试”，释放业务槽位，保留输入。不要无限等待且不向用户解释。

`process_csv()` 完成时先统计四项产物大小，合计超过预算就终止发布。若希望处理期间控制峰值，还要把写出方式改成可统计的流式/分块写出，并设置 worker 临时目录与内存的主机级限制；不能仅靠最终大小校验声称计算资源已受限。

### 成功与失败

- 每项长期产物写入成功，就用唯一事件从 reserved 转为 used。全部发布时释放本操作剩余额度，终结业务槽位。
- 输出失败或旧 token 被拒绝，已经写入的文件进入 delete_pending，仍计 used；未使用预算可关闭释放。无法确认的写入继续受登记预留保护。
- failed/succeeded/quarantined 释放业务槽位时，用唯一事件防止 finish、租约恢复、清理同时重复释放。
- 自动恢复保持同一逻辑活跃任务槽位，旧执行的文件预算先保留或回收，新执行必须另行预留，不能把旧残留当成免费空间。
- 显式手动 retry 需要原子获取新槽位和当日次数，再从 failed 转 queued；失败要整体回滚。输入过期、已隔离、被清理时不能重试。

若任务在第一个文件写完后进程消失，后续清理通过 FileAsset 与 QuotaEvent 对账，不靠猜测“失败就全部减掉”。

## 6. 并发事务设计

PostgreSQL 行锁会在事务结束时释放，`FOR UPDATE` 可串行化对同一配额行的修改，依据见参考 [1]。本方案建议锁序与 [总览](README.md) 一致。

设计伪代码，不是可直接粘贴的业务实现：

```python
with db.begin():
    quota = lock_user_quota(user_id)  # SELECT ... FOR UPDATE
    daily = lock_or_create_daily_usage(user_id, utc_date)
    existing = find_reservation_by_operation(operation_id)
    if existing:
        return existing
    require_capacity(quota, daily, requested_bytes, slot=1, submission=1)
    create_reservation_and_unique_event(operation_id)
    apply_reserved_counters(quota, daily)
# 外部 I/O 在事务提交后执行
```

锁同一个用户配额行也要先于 `DailyUsage`，避免跨日期边界竞争。reservation 保存原始 UTC 日期；23:59 创建、次日取消时，归还的是原日 reserved，不能错误扣减新一天。

过期预留不能只按时间直接清零。必须核对其 FileOperation、Job、写入租约和存储对象，先关闭写入/发布权限，再结算确认存在的文件、安排删除并释放真正未使用的余额。

## 8. 存量初始化与对账

1. 新表上线时先以观察模式统计，不拒绝现有请求。
2. 为每个用户创建额度行，按 FileAsset 中确认存在的所有文件回填 used，不仅统计 succeeded。
3. 对 queued/running 回填一个槽位；对仍在进行的上传和写入回填 reservation。迁移期间短暂停止新提交或使用账务事件水位，防止边扫描边写导致漏算。
4. 比较数据库账本、实际存储清单及活跃任务数量；未知对象进入 04 的候选流程，不盲目平均分摊给用户。
5. 账实一致后启用拒绝规则；先低流量用户，再全量。
6. 定期生成差异报告。纠偏使用审计事件和受控事务，不能定时把 used 重算覆盖，覆盖过程可能冲掉正在发生的结算。

回滚可先关闭“拒绝新增”开关，继续记账与对账。不要删除 reservation/事件表，也不要回退到不记账的旧 worker 与新 API 混跑。

## 9. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 只剩 10 MiB，两台 API 同时各预留 10 MiB | 恰好一个成功，不出现负数或超卖 |
| 两个相同幂等键并发上传 | 只有一个业务任务、一次每日计数；残留对象删除后账实一致 |
| 输出成功写入两项后 worker 崩溃 | 两项计 used，其余额度保持可核验，清理后准确释放 |
| 同一清理消息重复执行 5 次 | 只减少一次空间，不出现负数 |
| 手动 retry 与清理并发 | 要么完整取得槽位并保留输入，要么返回明确不可重试 |
| 23:59 预留，00:01 取消 | 归还原日预留，新日计数不受影响 |
| failed 输入仍存在、结果已删除 | 只保留输入占用，业务槽位已释放 |
| 配额不足生成结果 | 无 succeeded，无半成品下载，错误可理解 |
| PostgreSQL 两个独立连接并发提交 | 验证真实行锁和事务边界；不能只依赖 SQLite |
