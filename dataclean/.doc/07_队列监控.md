# 07 队列监控：从业务积压定位到执行故障

> 状态：实施指南，尚未实现。先做业务统计与执行历史，再增加 Flower、Prometheus 和告警。

## 1. 当前实现与一个重要区别

当前 [dispatcher.py](../app/dispatcher.py) 扫描数据库 queued 行，再发送 Celery 消息；它允许重复投递。[jobs.py](../app/jobs.py) 用数据库条件更新决定谁真正执行。`/health` 只检查数据库，没有业务积压、worker 活性或投递观测。

`process_job()` 会捕获业务异常，保存 Job.failed 并返回 False；Celery 包装函数正常返回时，Celery 可能记为 task-succeeded。因此“Celery 成功事件数”不能直接作为“销售报表生成成功数”。

同样，Redis 队列长度不等于业务待办量：消息可能重复、预取、执行中或尚未由 dispatcher 发送。核心指标必须从 PostgreSQL 业务记录获得，Celery events 用于辅助定位节点与消息。

## 2. 分阶段建设

### 第一阶段：无需完整监控栈

增加只读管理员概览、JobAttempt 与结构化日志。能回答：有多少 queued、最老等待多久、哪些 running 租约即将过期、最近有哪些错误、dispatcher 是否还在工作。

### 第二阶段：运维组件

使用独立的业务指标 exporter，从数据库读取聚合结果；Prometheus 抓取，Grafana 展示，Alertmanager 发出实际配置过的通知。Flower 在受控内网观察 Celery worker 和消息事件，不作为数据库业务状态替代。

Celery 官方介绍 inspect、events、Flower 及 worker heartbeat，见参考 [1]。启用事件会增加 broker 消息量，需要在测试环境验证开销。

### 数据采集与告警处理流程

```mermaid
flowchart LR
    W[抢占/心跳/结束事务] --> D[Job 与 JobAttempt]
    D --> E[业务 exporter 聚合快照]
    E --> P[Prometheus 抓取与规则判断]
    P --> G[Grafana 查看趋势]
    P --> A[Alertmanager 聚合通知]
    A --> H[运维结合日志与 Flower 排障]
    H --> V[修复后观察积压与错误是否恢复]
```

完整闭环是：业务状态变更时记录执行历史 → exporter 按周期读取并记录快照时间 → Prometheus 抓取 → 规则持续满足后通知 → 运维按 job_id/错误类别查受控日志 → 处理根因 → 观察等待时间、吞吐和成功率恢复。告警恢复不代表所有失败任务自动重试，后续动作遵循 08 的预算和管理员释放规则。

## 3. 建议新增数据

| 模型/字段 | 用途 |
| --- | --- |
| `JobAttempt` | job_id、run_token、attempt_no、worker_id、claimed_at、started_at、heartbeat_at、finished_at、outcome、error_code |
| `Job.queued_at` | 最新一次排队时间；不能一直用原始 created_at 衡量手动重试等待 |
| `Job.last_dispatched_at/dispatch_count` | 当前代次最近投递尝试与次数，08 补充 dispatch_generation |
| `ServiceHeartbeat` | 服务角色、受控 instance_id、last_seen_at、版本；dispatcher 和维护进程更新 |
| 可选 `MetricAggregate` | 长期累计计数/直方图桶，防止历史记录回收后累计值减少 |

`(job_id, run_token)` 唯一。Attempt 在抢占事务中创建；租约心跳同时更新本次执行，finish 与业务结果在同事务结束 Attempt。重复消息没有抢占成功时记录“跳过”指标，不伪造业务执行。

worker 被杀时，恢复器把原 Attempt 标为 lease_lost，并记录恢复原因；旧执行后来返回也不能把新 Attempt 改为成功。异常堆栈放受控日志，不写入面向普通用户的错误文本。

## 4. 首版指标表

以下指标都是**建议新增**，名称用于统一实现和告警，不代表现有 `/metrics` 已提供。

| 指标 | 类型/来源 | 解释 |
| --- | --- | --- |
| `dataclean_jobs{status}` | Gauge，DB | 每种业务状态的当前任务数，含后续 quarantined |
| `dataclean_ready_jobs` | Gauge，DB | queued 且 next_run_at 已到、文件有效、依赖允许执行的数量 |
| `dataclean_queue_oldest_wait_seconds` | Gauge，DB | 可执行 queued 的最大等待；无待办返回 0 |
| `dataclean_running_lease_overdue` | Gauge，DB | running 但租约已经过期的数量 |
| `dataclean_attempts_window{outcome}` | Gauge，DB | 最近 15 分钟结束的执行次数；不是累计 Counter |
| `dataclean_execution_p95_seconds` | Gauge，DB | 最近 15 分钟有效样本的执行耗时 P95 |
| `dataclean_execution_window_samples` | Gauge，DB | P95 使用的样本数，小样本时不触发耗时告警 |
| `dataclean_service_last_heartbeat_timestamp_seconds{role}` | Gauge，DB | 关键服务最近心跳的 Unix 时间戳；管理页另列实例明细 |
| `dataclean_dispatch_errors_window{reason}` | Gauge，审计/聚合表 | 投递错误，reason 是枚举 |
| `dataclean_metrics_snapshot_timestamp_seconds` | Gauge，exporter | 最近聚合成功的 Unix 时间戳，便于计算快照陈旧时间 |
| `dataclean_cleanup_pending_bytes` | Gauge，DB | 待回收字节，连接 03/04 |
| `dataclean_dependency_circuit_open{dependency}` | Gauge，DB | 连接 08 的熔断状态 |

等待时间需要区分人为退避等待与真正调度积压。08 新增 next_run_at 后，ready 队列的等待可定义为 `now - max(queued_at, next_run_at)`；另展示全部 queued 和延迟队列数量，避免隐藏大规模等待。

执行时长从 Attempt 的开始到结束计算；租约丢失和业务失败分别统计。P95 样本数不足例如 30 时仍可展示，但不按其触发性能告警。历史累计量如果需要 `rate()`，必须另实现 Counter/Histogram 与可持续聚合，不能对上述窗口 Gauge 使用 rate。

心跳和快照新鲜度用 `time() - ..._timestamp_seconds` 计算，避免采集循环卡住后“年龄值”也停止增长。按 role 聚合的最近心跳只能说明至少一个实例活跃，还要结合 ready 积压、running 数及管理页实例清单判断是否损失部分容量。

## 5. 指标采集架构与多进程

推荐首版将数据库业务指标放到单独 exporter 进程，每 15 秒生成一次聚合快照，由 `/metrics` 读取。数据库查询应批量聚合、有索引、不全表加载 pandas；单次采集失败保留可识别的陈旧快照并暴露采集失败状态，不伪造全部为 0。

所有 API 副本都对同一全局 DB 计数再相加，会把任务数翻倍。将业务 exporter 作为明确的单一采集目标；若部署多副本，设计主节点或查询去重，不能直接 sum 所有重复全局快照。

API 的 HTTP 请求数/延迟属于每进程指标，可另采集。Celery 默认多进程池也有相同问题：Python 全局变量里的计数不自动跨进程汇总。需要时按官方 Python client multiprocess 文档配置独立目录和进程退出处理，不能只给每个子进程导入 Counter 就声称全量可见，见参考 [3]。

Histogram 是扩展选项：在成功抢占后的实际业务 finish/lease_lost 事件上记录一次，按 outcome 分类；不按 Celery 正常返回重复计数。若从 DB 轮询生成直方图，必须有持久事件游标/聚合账本，避免每轮对同一次执行重复 observe。

Prometheus 官方建议控制标签基数，见参考 [2]。不要把 user_id、job_id、文件名、邮箱、run_token、原始异常文本作为 metric label。将这些放入有权限和保留期的日志，通过 request_id/job_id 关联。

## 6. 告警建议与排障动作

阈值只是初始示例，必须结合单任务耗时与实际到达率调整。

| 告警 | 示例条件 | 人工处理方向 |
| --- | --- | --- |
| 业务积压 | 最老可执行任务等待超过 120 秒，持续 5 分钟 | 检查 dispatcher、worker、配额、熔断与吞吐 |
| worker 不活跃 | 有 ready 任务且无新心跳，持续 2 分钟 | 查容器、内存、进程和网络 |
| 租约过期堆积 | overdue > 0，持续两个租约观察周期 | 查续约 DB 延迟、恢复器是否运行 |
| 执行错误增长 | 15 分钟至少 20 次执行，非用户数据错误比例超过 20% | 按错误枚举查依赖/发布故障 |
| dispatcher 停止 | 心跳年龄超过约定阈值 | 查进程与 broker 连通 |
| 清理停滞 | delete_pending 最老时间超过目标 | 查权限、版本控制和存储错误 |
| 指标失明 | exporter down 或快照超过 60 秒未更新 | 先修复采集，不能当作业务正常 |

示例 PromQL，字段与指标需先实际实现：

```promql
# 在 Prometheus 告警规则中另配置 for: 5m
dataclean_queue_oldest_wait_seconds > 120

# 就绪业务存在且业务 running 为 0，作为排障信号
(dataclean_ready_jobs > 0)
and on() (sum(dataclean_jobs{status="running"}) == 0)

# 快照采集停止，即使 /metrics 仍能响应也能发现
time() - dataclean_metrics_snapshot_timestamp_seconds > 60
```

错误率 Gauge 按同一 15 分钟窗口计算，并检查最小样本，不能将业务数据校验失败与基础设施错误混在一起自动重启服务器。告警聚合按服务/依赖，避免每个 Job 单独发通知。

## 7. Flower 与安全访问

建议在 Linux 容器运行 Flower，显式连接同一 broker，worker 启用事件，例如在现有 worker 命令追加 `--events`；是否启用 task-sent 事件单独配置和验证。

只读诊断命令示例，运行前确认服务名和实际 Celery app：

```powershell
docker compose exec worker celery -A app.celery_app:celery_app inspect ping
docker compose exec worker celery -A app.celery_app:celery_app inspect active
docker compose exec worker celery -A app.celery_app:celery_app inspect reserved
docker compose logs --tail 100 dispatcher worker
```

inspect 无响应只说明本次检查未取得节点响应，应结合 DB 心跳、broker 与进程判断，不能立刻宣布 worker 已死亡。

Flower、Grafana、Prometheus 和 `/metrics` 只在受控内网或已认证反向代理后可访问，不直接公开到互联网。Flower 可能提供任务管理能力，不能把它当成普通用户页面，也不要在不知道影响时 purge 队列。

## 8. 健康检查如何拆分

- `/health/live`：进程能响应，用于判断是否卡死。
- `/health/ready`：当前 API 能否完成其承诺的同步工作，至少数据库可用；上传必须依赖 OSS 时还要按合适策略反映存储不可用。
- `/health/dependencies` 或管理概览：显示 Redis、worker、dispatcher、OSS、邮件等详细状态，限制访问。

当前设计允许 Redis 故障时将任务持久保留为 queued，因此不能只因 broker 临时不可用就把整个 API 标为不可用并阻断查询。认证入口采用 06 的单独 503 规则，上传依赖按实际存储模式判断；不要用一个全局布尔值混淆所有能力。

当前 User 没有管理员角色；若增加管理页面，需要同时设计受控 role/is_admin、首次管理员引导和审计，不能按“已登录”就开放全部队列明细。首版可只对内部运维开放聚合 exporter，不增加管理页面。

先上线日志和 DB 聚合，再启用 dashboards，最后对已演练的阈值启用告警。关闭监控不应影响任务执行；新增记录必须与业务事务兼容，不能为了指标写入单独异常而把成功文件状态改为失败。

## 10. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| CSV 数据错误而 Celery 正常返回 | DB failed、业务失败统计正确，不被 Celery SUCCESS 覆盖 |
| 同一消息重复投递 10 次 | 只产生一次真实 Attempt，跳过消息单独统计 |
| 停 dispatcher | queued 最老等待增长，心跳告警可定位 |
| 停 worker 或强杀执行进程 | 能看到活性下降、租约失效与恢复历史 |
| Redis 停机 | 投递错误可见，DB queued 不丢失，API 能查询 |
| exporter DB 查询失败 | 明确采集失败/陈旧，不输出假 0 |
| 两个 API、多个 worker 子进程 | 业务数量不翻倍，进程指标不漏计 |
| 产生大量 job_id | 指标标签数量不随任务无限增长 |
| 未登录或普通用户访问管理明细 | 拒绝；无邮箱、文件名等越权泄露 |

演练停止容器等操作只在测试栈执行。文档中的故障场景尚未在本轮执行。
