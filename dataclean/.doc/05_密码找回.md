# 05 密码找回：验证邮箱与一次性重置链接

> 状态：实施指南，尚未实现。发布前应具备 [06 登录限流](06_登录限流.md) 中的发送与重置限流。

## 1. 当前账号模型的限制

现有 [models.py](../app/models.py) 的 User 只有 username、password_hash 和创建时间，没有邮箱。`POST /api/auth/register` 只接收用户名与密码。[security.py](../app/security.py) 已使用 Argon2id 与 JWT，但 JWT 中没有撤销版本。

因此不能只增加“输入用户名发送找回链接”：必须先建立可信的恢复渠道。本文选择验证邮箱；原密码不可取回，只能设置新密码。

## 2. 用户可见流程

### 新用户

注册时填写邮箱 → 发送验证链接 → 用户点击证明控制该邮箱 → 账号标记邮箱已验证 → 此后允许通过邮箱恢复密码。邮箱验证和密码重置使用不同用途的令牌，禁止互换。

### 存量用户

已登录用户进入账号设置 → 再次验证当前密码 → 填写邮箱 → 点击验证链接。验证成功后才能用于找回。

已经忘记密码、且历史上没有绑定验证邮箱的账号，不能凭刚填写的新邮箱证明身份。首版提示“该账号需通过既有人工恢复流程处理”；如果没有可靠身份核验渠道，就不能承诺恢复。禁止自动将用户名或浏览器提供的邮箱当作所有权证据。

### 忘记密码

用户输入邮箱 → 页面统一提示“如果该邮箱可用于恢复，我们会发送邮件” → 收到一次性链接 → 输入新密码 → 成功后返回登录页重新登录。成功时发送密码已更改通知，不自动登录。

这些原则与 OWASP 的统一响应、一次性令牌、避免枚举、重置后会话处理建议一致，见参考 [1]；具体字段与事务采用下面的项目设计。

## 3. 建议数据模型

| 模型 | 新增字段 |
| --- | --- |
| User | email、email_normalized、email_verified_at、auth_version，默认 0 |
| EmailVerificationToken | user_id、token_hash、purpose、expires_at、used_at、created_at |
| PasswordResetToken | id、user_id、token_hash、expires_at、used_at、created_at、created_request_id |
| MailOutbox | id、kind、user_id、token_record_id、encrypted_payload、state、attempt_count、next_attempt_at、expires_at、provider_message_id |
| SecurityAudit | user_id、event、request_id、time、受控来源信息；不保存原始 token 或密码 |

`email_normalized` 对已绑定邮箱建立唯一策略；建议首版每个可恢复邮箱只绑定一个账号。规范化按明确规则执行，不擅自删除 `+tag` 或合并点号不同地址，避免把不同邮箱合并。唯一冲突对外提示要谨慎，账号设置中的反馈也要避免大规模枚举。

token_hash 全局唯一，按用户和有效期建索引。密码重置表只保存摘要，例如 SHA-256 摘要；随机 token 使用密码学安全随机数，建议至少 32 字节。用户密码继续走现有 Argon2id，不把 token 摘要算法直接用于密码。

## 4. 请求重置的后端流程

建议新增 `POST /api/auth/forgot-password`，接收邮箱。

1. 统一校验格式与长度，执行来源 IP、规范化邮箱维度的限流。
2. 不因邮箱是否存在返回不同状态、正文或同步发送时延；通常返回相同 202。不要返回“邮箱未注册”“邮箱未验证”。
3. 对有效且已验证的账号，按账号加锁生成新 token，示例有效期 15 分钟。首版可作废该账号之前未消费的重置令牌，避免邮件多次申请后含义不清。
4. 在同一数据库事务里保存 token_hash、失效旧 token，并插入邮件 outbox。生成 URL 使用受信任的 `DATACLEAN_PUBLIC_BASE_URL`，不能拼接任意 Host 请求头。
5. 由独立邮件发送器取 outbox，调用阿里云邮件服务或已选 SMTP 服务。发送器不能依赖 CSV 工作队列，否则积压时用户无法恢复账号。
6. 邮件失败有明确次数预算、next_attempt_at、到期放弃与告警。记录服务商 message ID；“服务商接收”不等于“已送达收件箱”。

### 一次性 token 与可靠发信的冲突

发送器需要拿到原始 token 才能构造链接，但重置表不能存明文。建议 outbox 仅短期保存**应用层加密**的邮件敏感载荷，由单独密钥解密发送；发送完成、令牌过期或旧令牌失效后删除载荷。密钥不与数据库备份放在一起，日志中屏蔽 token。

如果首版不做加密 outbox，可选择同步发信并明确其可靠性限制，但不能同时声称“数据库只存 hash”又让异步发送器从 hash 还原 token。也不能把明文重置链接直接塞进持久 Redis 队列而忽略敏感信息暴露。

发送器在取件前复核令牌未过期、未使用、未被新申请替代。即便旧邮件已在途，旧链接也会因数据库状态被拒绝。

## 5. 确认重置与并发消费

建议新增 `POST /api/auth/reset-password`，接收 token 和新密码。

1. 限制请求体长度，并执行 IP/令牌维度限流。令牌格式错误、过期、已使用都返回统一的 `invalid_or_expired_reset_token`。
2. 对新密码使用与注册一致的长度与哈希策略，额外检查所需产品密码规则。不要发短信/邮件传明文密码。
3. 计算 token hash；读取关联 user_id 供锁定，事务中按固定顺序锁 User，再锁 token 并重新检查。所有重置/新申请/改密都遵循同样顺序。
4. 使用数据库时间判断 expires_at，确认 used_at 为空，然后更新 password_hash、标记 token 已使用、作废该用户其余重置令牌、增加 auth_version。
5. 同事务插入审计和“密码已修改”通知 outbox 后提交。两个并发请求消费同一 token 只能一个成功。
6. 返回成功后要求重新登录。`auth_version` 更新后的旧 JWT 在下一次 API 验证时拒绝。

为避免持锁计算高成本 Argon2，可先做格式校验和摘要查询，在事务外生成新密码哈希；最终事务必须重新检查 token。是否允许相同密码等产品规则应明确，不能为了规避竞争跳过一次性消费。

## 6. JWT 撤销与权限入口

在 [security.py](../app/security.py) 的签发函数中加入 `ver=user.auth_version`。当前 `decode_token()` 只向调用方返回用户标识，需同步改为返回经过验证的 claims 或明确的 `(user_id, auth_version)` 结构；保留现有算法、issuer、过期时间检查，并验证 ver 为非负整数。`current_user()` 解码后查询用户，将 ver 与数据库 auth_version 比较。当前入口本就查询用户，可在此增加一致性检查。

新增版本后，重置密码、主动改密、受控账号恢复都会增加版本。所有 API、下载签名入口和新增管理入口都复用 current_user，不留绕过入口。

存量 JWT 没有 ver：建议切换时统一拒绝并要求重新登录，在发布说明中明确；不要永远把缺失版本当作 0 接受。已发出的 OSS 预签名链接遵循 01 的独立短期有效期，不会因 JWT 版本增加而立即撤销。

不要在 reset endpoint 成功前修改密码、锁账号或撤销会话；攻击者仅提交找回请求不能影响真实用户登录。

## 7. 前端与链接保护

在现有 `app/static/` 的页面结构内增加“绑定/验证邮箱”“忘记密码”“设置新密码”入口，保持当前简洁工作台风格。

- 重置页使用 HTTPS，不加载第三方脚本或统计像素；设置 `Referrer-Policy: no-referrer`。
- 链接可将 token 放在 fragment，由同源脚本读取后 POST 到后端；随后用 `history.replaceState` 清理地址。不要把原 token 写入 localStorage。
- 对邮件扫描器只展示页面，GET 不消费 token，不在打开链接时立刻修改密码。
- 提交时展示成功、过期和限流提示；禁用按钮只是交互措施，不能替代后端一次性消费。
- 邮箱变更需要验证旧身份和新邮箱；更新后通知旧邮箱，按风险规则决定是否增加 auth_version。

## 9. 迁移与回滚

邮箱字段先可空，不为存量用户编造邮箱；部署绑定流程和统一提示后再启用找回。auth_version 回填为 0，再切换新 JWT 协议并强制一次重新登录。

功能关闭时停止新申请、继续保护 token 和加密载荷；不能回滚到不检查 auth_version 的旧鉴权代码，否则已经撤销的 JWT 可能恢复有效。密码哈希已更新的事实不会随界面回滚撤销。

## 10. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 不存在、未验证、已验证邮箱申请 | 对外相同状态与正文；无明显同步发送时间差 |
| 两个请求同时消费同 token | 仅一次成功，密码/版本/审计原子一致 |
| 过期、已使用、伪造、用途不符 token | 均拒绝，不修改密码 |
| 成功重置后调用旧 JWT | 401，旧下载签名签发入口同样拒绝 |
| 仅发起找回但未确认 | 原密码与原会话仍可使用 |
| 邮件失败、发送器重启或重复取 outbox | 有受控重试，不重复消费令牌，不记录明文链接 |
| Host 头伪造为攻击者域名 | 生成链接仍使用固定可信 PUBLIC_BASE_URL |
| 已忘记密码且没绑定邮箱的旧账号 | 不允许自行绑定新邮箱接管账号 |
| 邮件扫描器 GET 链接 | 不消费 token |
| 数据库备份/日志检查 | 重置表只有摘要，outbox 载荷加密且会到期清除 |

测试优先使用假邮件服务捕获链接；真实发送仅用测试账号和明确授权的邮件服务。密码找回上线必须验证鉴权失败、并发消费和实际邮件可达性。
