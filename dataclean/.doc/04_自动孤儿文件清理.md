# 04 自动孤儿文件清理：回收无有效引用的残留

> 状态：实施指南，尚未实现。依赖 [01 文件操作登记](01_多机对象存储.md) 和 [02 配额账本](02_用户配额.md)。

## 1. 孤儿文件从哪里来

[jobs.py](../app/jobs.py) 已在 finally 中清理本次临时目录，并在数据库确认最终目录未被引用后才删除。这能处理正常异常，却不能保证进程被强杀、机器掉电时运行 finally。

典型残留包括上传的 `.part`、未创建 Job 的输入、旧 run_token 的产物、只上传成功一部分的 OSS 输出，以及数据库提交确认丢失后保守保留的目录。原先没有全盘/全 Bucket 扫描与安全回收流程。

“孤儿”是**已无合法引用且无有效写入者的对象**。它不同于 03 中“仍有合法任务引用但已经过保留期的文件”。单次查询没有引用，不能直接证明可以删除。

## 2. 对象分类与处理原则

| 类别 | 处理原则 |
| --- | --- |
| Job.input_asset_id 或结果清单引用，且文件仍有效 | 保护，不进入孤儿删除 |
| 上传或执行操作 open、租约有效 | 保护，哪怕暂时没有 Job 正式引用 |
| 操作过期，但 Job 为当前有效 running/token | 先协调恢复或关闭操作，不能只按文件年龄删除 |
| 旧 token 文件且无结果清单引用 | 宽限期后复核并删除 |
| 已到期且仍有任务引用 | 交给 03 的保留期流程，不能擅自当孤儿删 |
| 未登记的 legacy/异常对象 | 进入候选清单，先观察与人工确认，默认不自动删 |
| OSS 未完成分片 | 使用分片清理策略，单独统计，不把它当成普通对象 |

建议扫描每 10 分钟运行一次，已登记且确认废弃的对象至少观察 24 小时；这是首版策略示例。时间宽限只能降低风险，真正安全依赖写入登记、状态围栏和删除前复核。

## 3. 建议模型与保护条件

复用 `FileOperation`、`FileAsset`，新增 `CleanupCandidate`：

| 字段 | 用途 |
| --- | --- |
| id、asset_id、backend、bucket、key、version_id | 精确候选身份，不用模糊前缀代表对象 |
| first_seen_at、last_checked_at、not_before | 首次发现、复核与最早删除时间 |
| reason、evidence | 过期操作、旧 token、无引用等原因和受控证据 |
| observed_size、observed_hash | 检测同位置文件是否已变化；ETag 不统一当作 MD5 |
| state | observed/approved/deleting/deleted/blocked |
| delete_generation、claim_expires_at | 多维护实例认领与过时执行隔离 |
| error_code、attempt_count、next_attempt_at | 明确失败与后续重试计划 |

对对象身份建立唯一约束；候选去重不能只用 key，因为版本可能不同。`FileOperation` 的持久记录要在第一次外部写入前创建，且写入者不能绕过操作状态自行发布。

正常业务只允许把 open 操作下完整 staged 的 FileAsset 激活。进入 abandoned/cleaning 的操作和 delete_pending 的 FileAsset 永远不能再被重新引用；需要重做时使用新的操作与对象键。

## 4. 完整清理流程

### 第一步：发现候选

优先从数据库查过期 FileOperation、长期 staged、旧执行文件及 delete_pending，不先全量列整个 Bucket。分批列对象可作为对账补充，只扫描自己的环境前缀；记录分页游标，限制每轮扫描和删除量。

节点本地临时目录也要扫描，但范围限定在配置的服务专用根目录。解析后的绝对路径必须仍位于该根目录；不跟随指向目录外的符号链接，不对无法识别归属的目录做递归删除。

### 第二步：只观察

写入 CleanupCandidate，不立即删除。记录发现时的操作 ID、Job、run_token、大小、版本与发现原因。先上线 dry-run，管理员查看候选清单，确认没有活跃上传和已成功任务。

### 第三步：认领并关闭发布权

候选达到 not_before 后，按统一锁序重新查询 quota、Job、operation 和 assets，复核：

1. 没有 Job 正式引用；或已由合法保留期流程授权回收。
2. 上传/写入租约无效；不存在当前合法执行仍可发布该对象。
3. 文件身份与发现时一致，候选未被其他批次完成。
4. 数据库可正常读取；任何关键查询失败都停止删除，不能将“查询失败”当作“没有引用”。

确认后，将操作从 open 变 abandoned/cleaning，并增加 fencing_version；将本批资产置 delete_pending、保存删除代次。事务提交后再外部删除，禁止持有行锁等待 OSS。

### 第四步：删除并结算

逐个删除精确对象/版本，确认结果后记录删除状态，以 `asset:<id>:deleted` 唯一事件释放配额。若删除请求结果不确定，保持 deleting，下一轮 HEAD/查询版本后再确认；对象已不存在可幂等完成，权限错误不能吞掉。

### 第五步：继续对账

保留 tombstone 和操作记录一段独立的对账窗口，不能删除一次就马上删光登记。旧进程可能在清理器关闭操作后才完成某个网络上传；它必须在发布 CAS 时失败，且不能再登记新合法引用。

如果旧写入后来才落到存储中，扫描器会在 tombstone 对账时发现它并再次删除，而不是因记录已为 deleted 就永远跳过。对象请求需要合理、可观测的连接与读写超时；不能把无限在途 I/O 当作可在任意时刻安全回收的已结束写入。

## 5. 解决“检查完又被引用”的竞争

设计伪代码：

```python
# 发现阶段只读，不代表已经获准删除
candidate = observe_asset(asset_id)

with db.begin():
    lock_in_shared_order(candidate.user_id, candidate.job_id,
                         candidate.operation_id, candidate.asset_id)
    require_no_committed_reference()
    require_no_live_writer()
    close_operation_and_increment_fence()
    mark_asset_delete_pending()
    claim_candidate_with_generation()

delete_exact_object_outside_transaction()
confirm_deletion_and_release_quota_once()
```

发布事务也必须检查同一组 FileOperation/FileAsset 状态。只有清理器使用锁，而上传者无条件写 Job 清单，仍然会产生误删。这项改造必须同时覆盖上传发布、worker 发布和存量迁移三个入口。

对当前本地实现，至少要新增写入意图和可核验的临时目录归属。仅使用目录 mtime 和“Job 不存在”推断孤儿，对慢上传和迁移任务并不安全。

## 6. 不同故障的处理

| 故障 | 处理 |
| --- | --- |
| 数据库不可用 | 停止所有删除，保留候选，报警 |
| OSS 权限拒绝 | 标记 blocked，保留账务占用，修复角色策略 |
| 删除超时 | 查询精确版本/对象，无法确认则保留 pending |
| 上传进程被强杀 | 操作租约到期后进入候选，再过观察期处理 |
| worker 租约过期但旧进程还活着 | 依靠 token 和操作围栏拒绝旧发布；清理其独立对象 |
| 本地文件大小/身份变化 | 中止该候选，重新调查，不按旧扫描结果递归删 |
| 扫描发现大量未知对象 | 先记录、分组和人工确认，不立即批量删除 |
| 同一候选被两实例认领 | 条件更新/短行锁只允许当前 generation 完成状态与账务 |

清理失败可以有限退避重试，例如 1、5、30 分钟后再次处理并进入人工告警；原因、上限和下一次时间必须显式保存，不能每秒无限轰击存储。

## 8. 上线、停用与观测

1. 先部署所有写入者的登记与围栏校验，确认已无旧版无登记写入者。
2. 对历史路径回填登记，无法确认的文件只观察。
3. dry-run 至少覆盖一次最长合法上传/执行/迁移窗口，并人为制造崩溃残留。
4. 从小批已登记的废弃对象启用真实删除，核对下载和配额。
5. 监控候选数、待删除字节、阻塞原因、最老 pending 时间、删除失败和 tombstone 后重新出现次数。

停用只关闭新认领，保留状态与账务。删除已发生则不能靠回滚代码恢复文件；恢复只能来自有效备份/保留版本，并且需要重建登记和引用。没有备份时应明确承认不可恢复。

## 9. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 上传很慢但正常续约，已超过候选年龄 | 不删除，不仅依赖 mtime |
| 上传完成后 DB 提交确认丢失 | 已引用对象受保护，待确认对象先保留 |
| worker 生成两项后被强杀 | 到期操作经过观察和复核后删除残留 |
| 清理器认领后旧 worker 上传才完成 | 旧执行不能发布；下一次 tombstone 对账删除迟到对象 |
| 清理发现无引用与发布事务同时进行 | 通过共同锁与状态围栏只允许一方获准 |
| 两个维护实例同时处理同候选 | 删除和扣账均幂等 |
| 数据库断连/权限查询失败 | 停止删除，不把异常视为无引用 |
| 候选目录链接指向服务根目录外 | 拒绝递归操作并记录原因 |
| 未知 legacy 对象 | 只进入观察/审批清单，不自动删除 |
