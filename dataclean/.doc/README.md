## 2. 当前基线

现有项目已经具备用户登录与任务归属校验、CSV 上传清洗、四种结果下载、任务分页、幂等提交、数据库条件抢占、租约恢复和 `run_token` 隔离。判断依据见 [models.py](../app/models.py)、[api.py](../app/api.py)、[jobs.py](../app/jobs.py)、[dispatcher.py](../app/dispatcher.py)。

当前文件保存在本地路径，Compose 中 api、worker、dispatcher 共用 `files` volume，见 [compose.yaml](../compose.yaml)。当前源码中没有上述 8 项功能的完整实现。原有项目验证结果不等于这些新增方案已验证。

## 3. 跨文档约定

以下是建议共同采用的模型，实施时只定义一次，各篇按职责补充字段。

| 模型 | 主要职责 | 首次引入 |
| --- | --- | --- |
| `FileOperation` | 在实际写文件前登记写入意图；记录 upload/job_run/migration、所有者、有效期、围栏版本和 open/committed/abandoned/cleaning/closed 状态 | 01，04 完善清理 |
| `FileAsset` | 登记单个输入或产物的存储位置、所属操作、执行令牌、大小、校验值、文件状态和删除结果 | 01 |
| `UserQuota` / `DailyUsage` | 用户配额配置、累计空间和每日提交计数 | 02 |
| `QuotaReservation` / `QuotaEvent` | 对操作预留空间，并以唯一业务事件结算或释放 | 02 |
| `CleanupCandidate` | 孤儿候选、首次发现时间、复核证据、删除进度 | 04 |
| `PasswordResetToken` / `MailOutbox` | 一次性密码重置、可靠邮件发送 | 05 |
| `JobAttempt` | 每次抢占、执行结果、错误分类、执行节点、耗时 | 07，08 扩展 |
| `DependencyCircuit` / `JobAudit` | 共享依赖熔断、管理员隔离与释放审计 | 08 |

统一语义：

- 数据库任务状态是业务真相。新增 `quarantined` 是执行状态；文件过期不新增任务执行状态。
- `Job.file_state` 建议取 `available/delete_pending/deleted`；是否允许访问还必须检查 `files_expires_at`。新任务提交前输入必须已确认完整。
- `FileAsset.state` 建议取 `planned/writing/staged/active/delete_pending/deleted`。`staged` 表示写完且尚未被任务正式引用；上传失败的部分对象进入删除流程。
- 每次执行使用新的 `run_token`，每次上传使用新的 operation ID；对象键不可复用。文件目录和对象键不是权限凭证。
- 所有时间按 UTC 保存，由前端按用户时区展示。示例中的 MiB 按 `1024 * 1024` 字节计算。
- 如果事务需要同时锁多张业务表，统一按 `DependencyCircuit → UserQuota → DailyUsage → Job → FileOperation → FileAsset/QuotaReservation → JobAttempt/QuotaEvent/JobAudit` 的顺序；同类记录按主键排序。没有涉及的表跳过。只读发现阶段可以不加锁，发生状态变更时再按顺序重新核验，不能从锁住的 Job 反向等待配额锁或熔断锁。账号重置使用独立的 `User → Token` 锁序，不与任务账务交叉持锁。
- 数据库事务内只做短小的校验、状态变更和账务写入，不持有行锁执行 OSS 上传、下载、邮件发送或 pandas 计算。
- 外部存储与数据库不具备本项目内的跨系统原子提交；采用先登记、私有写入、条件发布、失败补偿、定期对账的方式处理。

## 4. 推荐实施顺序

1. **存储基础**：实现 01 的统一文件登记与 LocalStorage 适配器，保留现有本地模式；再增加 OSS 适配器。
2. **资源与回收**：实现 02 的配额预留，再实现 03 的到期流程和 04 的孤儿清理。先观察候选，再启用实际删除。
3. **账号安全**：先实现 06 的限流服务，再发布 05 的验证邮箱、密码找回和 JWT 撤销版本；两项可以独立于存储开发。
4. **运行可靠性**：先做 07 的数据库监控和执行历史，再做 08 的故障分类、隔离及依赖熔断。

若只运行一台 ECS，01 中的 OSS 切换可以后置，但文件登记、配额、保留期、清理的语义仍应保持一致。首次部署不必一次引入所有运维组件。

## 5. 迁移、配置和验证的统一要求

### 数据库迁移

现有迁移入口是 [0001_users_jobs.py](../migrations/versions/0001_users_jobs.py)。不要重写已部署的 `0001`，也不要让 8 篇分别创建同名 `0002`。每完成一阶段，根据当前 Alembic head 新建 revision，保持单一顺序；若分支开发产生多个 head，先评审并合并迁移链。

通常按“增加可空字段/新表 → 兼容读写 → 分批回填与核对 → 启用规则 → 增加必要非空约束”的顺序推进。生产 PostgreSQL 行锁、索引、CHECK 约束的行为需要在 PostgreSQL 验证，SQLite 测试不能替代。

### 环境变量

新设置需要同时修改 `app/config.py`、`.env.example` 和部署配置。当前 Compose 用显式 `environment` 传参，仅往 `.env` 增加 `DATACLEAN_...` 不会自动把该参数传入容器。需要用 `${变量名}` 显式传给实际使用它的 api、worker、dispatcher 或新增维护服务；凭证按服务最小范围注入。

### 实施后验证

每篇的验收表是未来实施时的检查目标。优先扩展现有 `tests/test_auth_jobs.py`、`tests/test_workers.py`，再按模块增加独立测试文件。涉及并发、迁移、真实 Redis、真实 OSS 和多机的能力，需要相应集成证据。模拟存储成功不等于真实阿里云权限、网络和签名下载已验证。

纯文档交付只检查内容、UTF-8、Markdown 结构、相对链接与源码引用；无需重跑与本次文档无关的应用测试。

## 6. 如何使用这组指南

每次实施选一篇形成完整闭环：确认业务规则，按文件改动，运行该篇的验收，再更新项目说明。文档中的建议文件名表示未来新增入口，不代表这些文件已经存在。代码块标为“设计伪代码”时用于表达事务与顺序，不能直接复制后声称功能完成。
